## المشكلة الأولى: أرقام بتطلع فاضية رغم إنها موجودة في Google Search Console

### التشخيص — ٧ أسباب حقيقية في الكود القديم

#### ١. الربط بين الطلب والرد كان بالترتيب (أخطر سبب)

نود `Merge History` القديم كان بيعمل كده:

```js
results.forEach((r, i) => { const t = tasks[i]; ... });
```

يعني الرد رقم ٥ بيتحسب إنه بتاع الطلب رقم ٥ — بالترتيب وبس. ده بيقع في حالتين:

* **فشل على مستوى النود كله** (توكن منتهي، credential مش موجود): n8n بيطلّع **عنصر واحد** فيه الخطأ بدل ٥٢٥ عنصر. النتيجة: طلب واحد بس بياخد رد، و**٥٢٤ خانة بتفضل فاضية** من غير ما حد يعرف.
* **أي فرق في عدد العناصر** بيزحلق كل الردود اللي بعده، فالكلمة بتاخد رقم كلمة تانية أو خانة فاضية.

**الحل:** الربط بقى بـ `pairedItem` — الحقل اللي n8n نفسه بيحطه على كل عنصر خارج بيقول جه من أنهي عنصر داخل. ولو عدد الردود مش مساوي عدد الطلبات، الكود بيدخل **وضع صارم**: `pairedItem` بس، وأي طلب ملقاش رد بيتعلّم `missing` صراحةً بدل ما يتزحلق.

#### ٢. `alwaysOutputData: true` على نود `GSC Query`

الخيار ده بيخلي n8n يضيف عنصر فاضي `{}` لما النود ما يطلّعش حاجة. والكود القديم كان بيقرا `{}` على إنه **"رد ناجح من جوجل ومفيش ظهور"** → فيكتب `-` في خانة أصلها **فشلت**. يعني كان بيخفي الفشل ويحوّله لـ "مفيش ظهور مؤكد".

**الحل:** اتقفلت (`alwaysOutputData: false`) مع `onError: continueRegularOutput` — كده كل طلب فاشل بيطلّع عنصر فيه `error` حقيقي نقدر نمسكه. الفحص الساكن (`validate.mjs`) بيرفض أي بناء بيرجّعها `true` تاني.

#### ٣. الفترة كانت بتتحسب بتخمين (`LAG_DAYS`) مش ببيانات جوجل الحقيقية

* الشهري: `LAG_DAYS = 2`
* **الأسبوعي: `LAG_DAYS = 0`** والتشغيل يوم الإثنين للأسبوع اللي قفل الأحد.

بيانات GSC النهائية (`final`) بتتأخر عادةً **٢–٤ أيام**. يعني الرن الأسبوعي كان بيطلب من جوجل أسبوع **بياناته لسه ما وصلتش** — فآخر عمود كان بيرجع فاضي أو بأرقام ناقصة، كل أسبوع.

**الحل:** نود جديد `GSC Freshness` بيسأل جوجل نفسه:

```json
{ "dimensions": ["date"], "dataState": "final", "startDate": "<-25 يوم>", "endDate": "<النهاردة>" }
```

آخر تاريخ راجع = آخر يوم فيه بيانات نهائية فعلاً. الفترات بتتحسب على أساسه، فمش بنطلب فترة ناقصة أصلاً. لو السؤال ده نفسه فشل، بنرجع لـ `LAG_DAYS` (بحد أدنى ٣ أيام) وبنسجّل الملاحظة في التنبيه.

كمان موعد الرن الأسبوعي اتنقل من **الإثنين** لـ **الأربع ٨ صباحًا** — عشان بيانات الأسبوع اللي قفل الأحد تكون جاهزة.

#### ٤. الصفحة المستهدفة لما مكانتش ظاهرة كانت بتطلّع "مفيش ظهور"

الطلب لجوجل بيتفلتر بـ (الكلمة + الدولة) والنتيجة بتترجع مقسّمة على الصفحات. لو الرابط المكتوب في `Keywords` مش مطابق حرفيًا لأي صفحة راجعة (اختلاف في `www` أو السلاش الأخير أو الترميز أو الرابط اتغيّر) → الكود القديم كان بيرجّع `-`، رغم إن الموقع **فعلاً** ظاهر للكلمة دي على صفحة تانية — وده الرقم اللي الكلاينت شايفه في واجهة GSC.

**الحل:**

* تطبيع أقوى للروابط: فك ترميز مزدوج، شيل `#` و `?`، شيل `www` والبروتوكول والسلاش الأخير و `/index.html`.
* لو الصفحة المستهدفة برضه مش ظاهرة → بناخد **أعلى صفحة ترتيبًا** (مش أعلى كليكات) ونعلّمها في `pageMisses` وتوصل كملاحظة في الإيميل. النتيجة: اختلاف الرابط عمره ما يطلّع خانة فاضية.
* لو عايز السلوك القديم بالظبط، غيّر `PAGE_MATCH` في `Config` لـ `'strict'`.

#### ٥. `rowLimit: 100` وصفوف من غير ترتيب صالح

`rowLimit` كان ١٠٠ صفحة، وأي صف راجع كان بيتقبل زي ما هو حتى لو `position` = 0.

**الحل:** `rowLimit: 500`، `dataState: 'final'` صراحةً، والصف مابيتقبلش غير لو `position > 0` و `impressions > 0`. لو عدد الصفحات وصل للحد الأقصى بتوصل ملاحظة نرفع الحد.

#### ٦. أرقام الشيت كانت بتتقري بصيغة العرض

`Fetch Sheet` كان بيقرا بالصيغة الافتراضية (`FORMATTED_VALUE`) — يعني نص متنسّق حسب لغة الشيت. ودالة التحويل كانت `String(v).replace(/[^\d.\-]/g,'')`، اللي بتمسح **الأرقام العربية** (٠١٢٣) بالكامل → `null`.

**الحل:** `valueRenderOption=UNFORMATTED_VALUE` (أرقام JSON خام)، ودالة تحويل بتفهم الأرقام العربية والهندية، الفاصلة العشرية العربية (`٫`)، فاصل الآلاف العربي (`٬`)، ومحارف الاتجاه المخفية.

#### ٧. فشل قراءة الشيت كان بيمسح الأرشيف كله

`Fetch Sheet` شغّال بـ `onError: continueRegularOutput`. لو فشل، `$json.values` بتبقى `undefined`، والكود القديم كان بيكمل عادي بذاكرة تاريخية فاضية — وبعدين `Write To Sheet` بيكتب فوق الشيت. **يعني رن واحد فاشل كان ممكن يمسح كل الأرشيف.**

**الحل:** `Read Sheet` بقى بيفرّق بين "الشيت فاضي" و"مقدرناش نقراه"، وبيطلّع `__sheetError`. وبوابة الجودة بتوقف الرن قبل أي كتابة.

### الحل: ٦ طبقات حماية

```
Config → Verify GSC Access → GSC Access Check
                                ├─ فشل ──→ GSC Alert Email
                                └─ نجاح → GSC Freshness → Freshness Guard   ← طبقة ١
                                          → Keywords → Search Volume
                                          → Fetch Sheet → Read Sheet        ← طبقة ٢
                                          → Build Tasks → GSC Query         ← طبقة ٣
                                          → Collect Results → Needs Retry?  ← طبقة ٤
                                               ├─ فيه فشل → GSC Retry Query ─┐
                                               └─ مفيش ──────────────────────┤
                                          → Merge History                   ← طبقة ٥
                                          → Validate Data → Data Quality Gate ← طبقة ٦
                                               ├─ فشل ──→ Data Alert Email
                                               └─ نجاح → Write To Sheet → … → Send Report Email
```

| # | الطبقة | بتمنع إيه |
|---|--------|-----------|
| ١ | `GSC Freshness` | إننا نطلب فترة بياناتها لسه ما اكتملتش |
| ٢ | `Read Sheet` | إن فشل قراءة الشيت يتحوّل لمسح الأرشيف |
| ٣ | `GSC Query` (٥ محاولات / ٥ ثواني / timeout ٦٠ث) | الفشل المؤقت من الحصص والشبكة |
| ٤ | `Collect Results` + `GSC Retry Query` | إن طلب فشل يفضل فاشل — بيتعاد بمعدل أبطأ |
| ٥ | `Merge History` | الربط الغلط + تحويل الفشل لـ `-` + مسح الأرشيف |
| ٦ | `Validate Data` + البوابة | إن رن ناقص يكتب على الشيت أو يطلّع تقرير |

### الفرق الجوهري: خانة فاضية ≠ مفيش ظهور

القاعدة اللي الكود كله بيمشي عليها دلوقتي — وكل خانة بتتصنّف واحد من دول:

| التصنيف | يعني إيه | بيتكتب إيه في الشيت |
|---------|----------|--------------------|
| `ranked` | جوجل رد ومعاه ترتيب | الرقم |
| `no-data` | جوجل رد سليم ومفيش ولا ظهور | `-` |
| `from-archive` | السحبة فشلت والأرشيف فيه رقم | رقم الأرشيف |
| `kept-archive` | عمود قديم رجع "مفيش" والأرشيف فيه رقم | رقم الأرشيف + شبهة |
| `hole` | مفيش سحبة ولا أرشيف | **فاضية** |

**خانة فشل سحبها عمرها ما تتكتب `-` ولا `0`.** بتفضل فاضية، والرن الجاي بيعيد يجيبها، وبتتعدّ في التنبيه.

### حماية الأرشيف من التآكل

بيانات جوجل للشهور والأسابيع **المقفولة مابتتغيرش**. فلو السحبة رجعت "مفيش ظهور" لعمود قديم والأرشيف فيه رقم — السحبة هي اللي فيها مشكلة، مش التاريخ. الكود بيمسك رقم الأرشيف ويسجّلها في `suspicious`. آخر عمودين (`VOLATILE_TAIL`) مستثنيين لأن بياناتهم لسه ممكن تستقر.

### بوابة الجودة — الأرقام

في `Config`:

* `MIN_COVERAGE = 0.98` — أقل من ٩٨٪ خانات مكتملة = وقف.
* `MAX_HOLES = 12` — أكتر من ١٢ خانة فاضية = وقف حتى لو النسبة عدّت.

لما البوابة تقفل: **الشيت مابيتلمسش، والعرض التقديمي مابيتلمسش، والتقرير مابيتبعتش.** بيتبعت إيميل تشخيصي فيه سبب كل خانة فشلت. والرن الجاي بيعيد يسحب كل حاجة من أول (`REFETCH_LAST = COLUMNS`) فالنظام بيشفي نفسه.

## المشكلة التانية: تحديث الكلمات من ملف الإكسل

### المصدر

`seo-reports/keywords/source.xlsx` — ورقتين: `العوجان` و `شوق`.
سكريبت `extract-keywords.py` بيقراها ويطلّع `keywords/alojan.json` و `keywords/shoug.json`.

### النتيجة

| المشروع | قبل | بعد | الأقسام |
|---------|-----|-----|---------|
| العوجان | ٢٤ كلمة | **٣٥ كلمة** | ٦ |
| شوق | ١٣ كلمة | **٢٥ كلمة** | ٨ |

**أقسام العوجان:** أورام المخ والحبل الشوكي (٨) • الاستسقاء الدماغي (٨) • التحام عظام الجمجمة (٢) • الدروز الجبهي (١) • تجميل الجمجمة (١) • الرئيسية — كلمات تجارية (١٥)

**أقسام شوق:** الصفحة الرئيسية (٤) • مقال: أفضل محامية في الكويت (١) • قضايا تحصيل الأموال (١) • قضايا الأحوال الشخصية والأسرة (٦) • صياغة وتوثيق العقود (١) • افضل محامي تجاري بالكويت (٤) • افضل محامي جنايات في الكويت (٣) • محامي استشارات مجانية (٥)

الصف رقم ٢١ في ورقة شوق فاضي (رقم من غير كلمة) — اتتخطى.

### حاجات اتحلّت مع التحديث

**عدد مرات البحث بقى شغّال.** نود `Search Volume` كان كل خاناته فاضية، فالسلايدز كانت بتطبع `—` دايمًا. دلوقتي القيم جاية من عمود `SV ( SA )` في الإكسل مع كل كلمة. نود `Search Volume` فضل موجود كـ **تعديل يدوي** — أي قيمة تكتبها فيه بتكسب على قيمة الإكسل.

**الشيت مابيسيبش بقايا الكلمات القديمة.** `Write To Sheet` بيستخدم `PUT` اللي بيكتب فوق النطاق المكتوب بس. لما قايمة الكلمات تقصر، الصفوف الزيادة كانت بتفضل في الشيت للأبد. دلوقتي `Read Sheet` بيسجّل مقاس الشيت القديم، و`Validate Data` بيبطّن القيم لحد المقاس ده بخانات فاضية — فالزايد بيتمسح في نفس الكتابة الذرّية (من غير خطوة مسح منفصلة تسيب الشيت فاضي لو الكتابة فشلت بعدها).

**عمود `Article` جديد في الشيت.** الترويسة بقت `Country | Section | Keyword | Page | Article | …` — عمود الصفحة/المقالة المستهدفة من الإكسل. قراءة الأرشيف مربوطة بترويسات الأعمدة بالـ regex مش بأرقام الأعمدة، فالبيانات القديمة بتتقري عادي.

**روابط الصفحات.** العوجان: الإكسل مافيهوش روابط مؤكدة → الرابط فاضي والكود بياخد أعلى صفحة ظاهرة للكلمة. شوق: الروابط المؤكدة من الأوتوميشن القديم اتحطت للأقسام اللي نعرفها (الرئيسية، الأحوال الشخصية، مقال أفضل محامية)، والباقي فاضي.

### إزاي تعدّل الكلمات بعدين

```bash
# ١) عدّل seo-reports/keywords/source.xlsx
python3 seo-reports/extract-keywords.py     # يقرا الإكسل ويطلّع JSON
node seo-reports/build.mjs                  # يبني ملفات n8n الأربعة
node seo-reports/validate.mjs               # فحص ساكن
node seo-reports/test.mjs                   # ٧٥ اختبار
# ٢) استورد dist/*.json في n8n
```

السكريبت بيقف بصوت عالي لو عدد المجموعات أو عدد الكلمات في كل مجموعة اتغيّر عن المتوقع، أو لو فيه كلمة مكررة — عشان ما تعدّيش أقسام غلط من غير ما تاخد بالك.

## المشكلة التالتة: الإيميل مابيوصلش على جيميل

### التشخيص

في نود `Emails` الحالي:

```
mailTo_1 = m.gamal.zaid1@gmail.com      ← مابيوصلش
mailCc_1 = M.gamal@rabeh.org            ← بيوصل
```

يعني القايمة نفسها سليمة — **الإيميل بيتبعت والسيرفر بيرفض المستلم الخارجي**، أو بيقبله والمستلم بيرميه.

السبب الجذري إن نود `Send Email` في n8n **بيعتبر الإرسال ناجح طالما السيرفر استلم الرسالة**، حتى لو رفض بعض المستلمين. nodemailer بيرجّع `{ accepted: [...], rejected: [...] }` والنود بيرمي الرد ده من غير ما يبصله. فالرن بيبان أخضر، والإيميل مش واصل، ومحدش يعرف.

### الحل — تلات مستويات

#### ١. نتأكد فعلاً مين استلم (النود الجديد `Delivery Audit`)

بيقرا رد الـ SMTP الحقيقي بعد الإرسال ويقارن المستلمين المتوقعين بالمقبولين:

* مستلم اترفض أو السيرفر سكت عنه → **بيتبعتله إيميل منفصل لوحده** (`Resend Individually`).
* الإرسال نفسه وقع (توثيق فشل مثلًا) → كل المستلمين بيتعاد لهم فرديًا.
* النتيجة النهائية بتتبعت في إيميل حالة توصيل (`Delivery Alert Email`) لعناوين الدومين الداخلي — اللي أكيد بتوصل — وفيه **جدول: مين وصله ومين لأ ورد السيرفر الحرفي لكل واحد**.

يعني بدل فشل صامت، بقى عندك سبب مكتوب: `550 5.7.1 Relaying denied` أو `535 Authentication failed`.

#### ٢. تقوية توصيل الرسالة نفسها

| التغيير | ليه |
|---------|-----|
| `emailFormat: both` + نسخة **نص عادي** | HTML لوحده من غير `text/plain` من أكبر عوامل رفع سكور السبام عند جيميل وأوتلوك. كل الإيميلات بقى ليها نسخة نصية كاملة. |
| `appendAttribution: false` | بيشيل سطر «This email was sent automatically with n8n» + اللينك — سطر إعلاني في رسالة تجارية = سكور سبام أعلى. |
| `fromEmail` باسم عرض: `"رابح — تقارير SEO" <M.gamal@rabeh.org>` | العنوان لازم يفضل **مطابق للمستخدم المصادَق عليه في SMTP** — أي اختلاف بيسبب رفض أو فشل SPF. |
| `replyTo` صريح | بيقلل احتمال التصنيف كسبام. |
| شيل التكرار بين To و CC | بعض سيرفرات SMTP بترفض المستلم المكرر. |
| تحقق من صيغة الإيميل في `Config` | عنوان غلط واحد كان ممكن يوقّف الإرسال كله — دلوقتي بيتشال وبيتسجّل. |
| إزالة الإيموجي من عناوين التنبيهات | `⚠️` في الـ subject بيرفع سكور السبام. |

#### ٣. الجزء اللي مش في الأوتوميشن

لو التنبيه لسه بيقول إن جيميل رافض، المشكلة في إعدادات السيرفر والـ DNS — راجع **[EMAIL-DELIVERABILITY.md](EMAIL-DELIVERABILITY.md)** فيه الفحوصات بالترتيب وأوامر جاهزة.

## المشكلة الرابعة: تنبيه فشل Search Console مكانش بيقول السبب

التنبيه القديم كان **نص ثابت** مكتوب في نود الإيميل نفسه: «الصلاحية غالبًا منتهية
أو فيه مشكلة في الحساب المربوط». يعني مهما كان السبب الحقيقي، الرسالة واحدة —
ومحدش يعرف يبدأ منين.

### الحل: فرع تشخيص حقيقي

```
GSC Access Check ──فشل──→ List GSC Sites ──→ GSC Diagnose ──→ GSC Alert Email
```

**`List GSC Sites`** بيجيب من جوجل قائمة **كل المواقع اللي الحساب المربوط شايفها
فعلاً** مع مستوى الصلاحية على كل واحد.

**`GSC Diagnose`** بيقارن اللي في `Config` باللي جوجل رجّعه، وبيطلّع سبب محدد وخطوة
محددة:

| رد جوجل | التشخيص | الخطوة |
|---------|---------|--------|
| `401` / `invalid_grant` / `revoked` | صلاحية الحساب انتهت أو اتسحبت | Reconnect لكريدنشيال `rabeh.seven.b` في n8n |
| نفس الدومين بشكل مختلف في القائمة | `SITE_URL` مش مطابق لشكل الموقع المسجّل | **بيديك النص الصح جاهز للنسخ** (مثلاً `sc-domain:aaalojan.com`) |
| الموقع مش في القائمة أصلاً | الحساب مالوش صلاحية عليه | ضيف الحساب في Search Console ← المستخدمون والأذونات |
| `403` | متصل بس بدون صلاحية | نفس الخطوة اللي فوق |
| `404` والقائمة كمان فشلت | الصلاحية واقعة أو الـ API مش مفعّل | Reconnect + فعّل Search Console API في Google Cloud |
| `429` / quota | تجاوز حد استخدام مؤقت | شغّله تاني بعد شوية (بيتصنّف `temporary`) |
| `ETIMEDOUT` / `5xx` | عطل شبكة مؤقت | شغّله تاني (بيتصنّف `temporary`) |

الإيميل الجديد فيه:

* **إيه اللي حصل بالظبط** — بالعربي، سبب واحد محدد.
* **إيه اللي تعمله** — خطوة واحدة، ومعاها اسم الكريدنشيال أو النص الجاهز للنسخ.
* **الموقع المطلوب** مقابل **جدول بكل المواقع اللي الحساب شايفها** ومستوى الصلاحية.
* **رسالة جوجل الخام** للفني.
* تطمين إن الشيت والعرض ما اتلمسوش.

الشكل الغلط للـ `SITE_URL` من أشهر الأسباب: جوجل بيعتبر
`https://www.aaalojan.com/` و `https://aaalojan.com/` و `sc-domain:aaalojan.com`
**تلات مواقع مختلفة تمامًا**. الجدول في الإيميل بيحسم الموضوع فورًا.
