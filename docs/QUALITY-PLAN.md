# خطة الجودة والاختبار — الوصول بـ DeepSeek إلى مستوى المقال المرجعي

---

## أولًا: تعريف «الجودة» تعريفًا قابلًا للقياس

«جودة 100% مطلقة» عبارة لا يمكن اختبارها، فأي حكم على مقال يبقى فيه جزء تقديري.
لذلك تُرجم الهدف إلى **ثلاث بوابات** يمكن قياس كل واحدة منها آليًا وتكرارها في كل دورة:

| البوابة | المعيار | من يقيسها |
|---|---|---|
| **١. البوابة الصلبة** | ٢٣ فحصًا رقميًا: صفر مخالفة حرجة، صفر ملاحظة → **درجة آلية 100%** | `tools/grade.mjs` — كود، بلا نموذج لغوي |
| **٢. بوابة اللائحة** | كل بند من ١٥ بندًا ≥ **8/10** وصفر Critical Issues | لجنة النقد + التدقيق النهائي داخل الـ workflow |
| **٣. بوابة المقارنة** | حكم أعمى على مقالين مجهولي المصدر: **تعادل أو تفوّق** على المقال المرجعي في ٦ بنود من ٨ | `tools/compare.mjs --judge` |

**«وصل DeepSeek»** تعني: اجتياز البوابات الثلاث في **ثلاث تشغيلات متتالية على ثلاثة مواضيع مختلفة**.
تشغيلة واحدة ناجحة صدفة؛ ثلاث تشغيلات متتالية نظام.

> المقال المرجعي: [`benchmark/gold/google-ads-ar.md`](../benchmark/gold/google-ads-ar.md) — كُتب يدويًا وفق المعايير نفسها،
> بخمسة مصادر حقيقية مُتحقَّق منها، ويحقق **100%** على البوابة الصلبة. وبجواره
> [`benchmark/samples/weak-baseline-ar.md`](../benchmark/samples/weak-baseline-ar.md) وهو مقال نموذجي بلا ورشة، يحقق **55%** —
> ليكون الفارق بين الطرفين معلومًا لا انطباعيًا.

## ثانيًا: ما الذي تغيّر في المحرك من أجل DeepSeek

DeepSeek ليس Claude، وله ثلاثة قيود حقيقية عولجت في الكود لا في البرومبت وحده:

### ١. سقف المخرجات 8192 توكن ← الكتابة قسمًا بقسم

مقال عربي من ٢٠٠٠ كلمة يقترب من سقف مخرجات DeepSeek أو يتجاوزه، فيخرج مبتورًا.
الحل: `llm.chunked_writing = true` يحوّل الورشة من «نداء واحد يكتب المقال» إلى **نداء لكل قسم**.

| | الوضع الكامل | الوضع المُجزَّأ |
|---|---|---|
| كتابة المسودة | نداء واحد ~٦٠٠٠ توكن | ٨ نداءات × ~٩٠٠ توكن |
| تمريرة السرد | إعادة كتابة المقال كله | كل قسم مع نهاية سابقه وبداية تاليه |
| دورة التعديل | إعادة كتابة المقال كله | كل قسم يتلقى الموجز وينفّذ ما يخصه |

ولم تتغيّر بنية الـ workflow ولا عدد العقد: عقدة n8n تُنفَّذ مرة لكل عنصر يدخلها،
فعقدة الأجندة تُخرج ثمانية عناصر وتُنفَّذ عقدة النداء ثماني مرات تلقائيًا.

**فائدة جانبية:** الانتباه المركّز على قسم واحد يرفع جودة كل قسم، ودورة التعديل تلمس الأقسام المعنية فقط بدل إعادة كتابة تُدخل انحدارًا في أقسام كانت سليمة.

### ٢. لا أحد يملك العدّ الإجمالي ← أهداف رقمية لكل قسم

في الوضع المُجزَّأ لا يرى أي كاتب المقال كله، فلا أحد مسؤول عن «١٩٠٠ كلمة» ولا عن «الكلمة المفتاحية ٨ مرات».
دالة `H.sectionTargets` تحسب الفارق الإجمالي وتوزّعه، فيصل كل كاتب قسم سطر تنفيذي:

<div dir="ltr">

```
- طول قسمك: 180 كلمة → المطلوب 240 كلمة (±10%)  ⇒ أضف ~60 كلمة من محتوى حقيقي، لا حشو
- تكرار «اعلانات جوجل ادوردز» في قسمك: 0 → المطلوب 2  ⇒ أضفها مرتين بصياغتها الحرفية
- (للسياق: إجمالي المقال الآن 1620 كلمة والمطلوب 1900)
```

</div>

هذا حوّل الملف التعريفي في المحاكاة من **رسوب دائم** إلى **نجاح في دورتين**.

### ٣. الحذف العرضي أثناء التقصير ← قائمة عناصر محمية

محرّر قسم مطالَب بحذف ١٣٠ كلمة سيحذف الفقرة التي تحمل رابطًا داخليًا.
لذلك تُرسَل مع كل قسم قائمة `H.protectedBlock`: نص العنوان، وكل رابط بصيغته الحرفية، والأرقام ومصادرها.

### فروق أخرى مضبوطة في الملف التعريفي

| البند | الضبط | السبب |
|---|---|---|
| `response_format: json_object` | مفعّل لكل شخصيات المراجعة | يرفع موثوقية قراءة JSON من النماذج الأضعف |
| `temperature_scale: 2.2` | 0.4 → 0.88 · 0.65 → 1.43 | سُلَّم حرارة DeepSeek يمتد إلى 1.5 للكتابة |
| `enable_tools: false` | لا أداة بحث | DeepSeek لا يوفّرها عبر الـ API |
| `research_lead` | برومبت «بلا اختلاق» | بلا أداة بحث، كل رقم غير مُرسَل → `unverified` |
| `auto_sources_section` | قسم المصادر يُبنى بالكود | يلغي فئة كاملة من أخطاء التنسيق والتطابق |
| `gate.max_rounds: 6` | بدل 4 | النموذج الأرخص يحتاج تكرارًا أكثر، وتكلفة الدورة أقل |

## ثالثًا: الأدوات

| الأمر | ماذا يفعل | يحتاج API؟ |
|---|---|---|
| `npm test` | بناء + تحقق بنيوي + محاكاة الملفات الخمسة | لا |
| `npm run grade -- --article=x.md --brief=b.json` | ٢٣ فحصًا على أي مقال من أي مصدر | لا |
| `npm run compare -- --gold=a.md --candidate=b.md --brief=b.json` | مقارنة وجهًا لوجه: الفحوص + بصمة الأسلوب | لا |
| `... --judge` | حكم أعمى بترتيب عشوائي على ٨ بنود | نعم |
| `node tools/simulate.mjs --live --profile=…` | تشغيل الورشة كاملة من الطرفية بنداءات حقيقية | نعم |
| `npm run bench -- --profile=…` | **الدورة كاملة**: تشغيل → تصحيح → مقارنة → مقابض الضبط | نعم |

`tools/simulate.mjs` محاكي n8n مصغّر ينفّذ **كود العقد نفسه** الموجود في الـ workflow.
فما ينجح في الطرفية ينجح في n8n، والعكس — وهذا ما يجعل دورة الضبط دقائق بدل ساعات.

## رابعًا: بروتوكول الدورة

<div dir="ltr">

```bash
export DEEPSEEK_API_KEY=sk-...          # المفتاح نفسه الموجود في كريدينشال n8n

npm run bench -- \
  --profile=rabeh_article_ar_deepseek \
  --brief=benchmark/briefs/google-ads-ar.json \
  --gold=benchmark/gold/google-ads-ar.md \
  --judge
```

</div>

كل تشغيلة تُنتج مجلدًا في `runs/` فيه `article.md` و`audit.md` و`minutes.md` و`pack.json` و`bench.json`،
وتُضاف سطرًا إلى `runs/ledger.jsonl` — فيصير تحسّن الجودة عبر الدورات **رقمًا يمكن رسمه**، لا انطباعًا.

### حلقة الضبط

```
تشغيل → قراءة المخالفات الباقية → تعديل مقبض واحد فقط → إعادة التشغيل
```

**عدّل مقبضًا واحدًا في كل دورة.** تغيير ثلاثة أشياء معًا يخفي أيها نفع.
`bench` يطبع مقبض الضبط المقترح لكل مخالفة باقية.

### ترتيب معالجة المخالفات

عالج بهذا الترتيب، فالأعلى يسبّب ما تحته غالبًا:

1. **مخالفات بنيوية** (`word_count` · `intro_words` · `h2_direct_answer`) ← مقابضها في المخطط وأهداف الأقسام.
2. **مخالفات الكلمات** (`primary_keyword_count` · `secondary_keywords`) ← الحصص وخريطة الكلمات.
3. **مخالفات الروابط والمصادر** (`links_whitelisted` · `internal_links_used` · `numbers_have_evidence`) ← `mandatory_citations` وبرومبت البحث.
4. **مخالفات الأسلوب** (`banned_phrases` · `dialect` · `visual_rhythm`) ← أضف ما يُرصد إلى القوائم فلا يتكرر.
5. **بنود اللائحة تحت 8/10** ← برومبتات الشخصيات المسؤولة عن تلك البنود تحديدًا.

### متى تتوقف

توقف عند تحقق أحد أمرين:

- **النجاح**: ثلاث تشغيلات متتالية على ثلاثة مواضيع تجتاز البوابات الثلاث → ثبّت الملف التعريفي.
- **السقف**: خمس دورات متتالية لا تحرّك الدرجة الآلية أكثر من نقطتين ← القيد في النموذج لا في البرومبت.
  عندها استخدم **الوضع الهجين** أدناه.

## خامسًا: الوضع الهجين — إن ثبت سقف DeepSeek

نقطة الضعف المتوقعة ليست البنية (البنية يفرضها المفتش الآلي عدديًا)، بل **الحكم النقدي**:
قدرة الناقد على قول «هذه الفقرة يمكن أن تجدها في أي موقع منافس» بدل إعطاء 9/10 لنص متوسط.

الحل الاقتصادي: **الكتابة على DeepSeek، والحكم على نموذج أقوى.** الكتابة تستهلك أغلب التوكنات، والحكم أرخص بكثير.

<div dir="ltr">

```js
// في src/profiles/… أو مباشرة في عقدة 📚 Profiles Registry
llm: {
  provider: 'deepseek',
  url: 'https://api.deepseek.com/chat/completions',
  model: 'deepseek-chat',              // الكتابة والتحرير
  chair_model: 'deepseek-reasoner',    // الحسم والتدقيق النهائي
  chunked_writing: true
}
```

</div>

`deepseek-reasoner` أعمق في الحسم. وإن أردت مزوّدين مختلفين للكتابة والحكم، فذلك يحتاج
عقدة نداء ثانية باعتماد مستقل — وهي إضافة صغيرة موصوفة في [`EXTENDING.md`](EXTENDING.md).

## سادسًا: التكلفة المتوقعة لكل تشغيلة

| الوضع | نداءات دورة أولى | كل دورة إضافية | الملاحظة |
|---|---|---|---|
| كامل (Claude) | ~٢٠ | +١١ | نداءات أقل، توكنات أكبر لكل نداء |
| مُجزَّأ (DeepSeek) | ~٣٤ | +١٩ | نداءات أكثر وأصغر — أرخص إجمالًا |

التقدير من المحاكاة: تشغيلة DeepSeek في دورتين ≈ **٥٨ نداءً**.
والأرقام الفعلية (التوكنات والزمن) تُسجَّل في `usage.json` داخل مجلد كل تشغيلة.
